Multi-hop memory recall: put the model in the retrieval loop and it ~quadruplesMulti-hop pamäťový recall: daj model do slučky vyhľadávania a takmer sa zoštvornásobí

June 25, 20264 min readAgent memory · Retrieval · LoCoMoAgentová pamäť · Vyhľadávanie · LoCoMo
The takeawayZhrnutie

On the full LoCoMo benchmark (276 multi-hop questions), flat similarity retrieval assembles the complete evidence chain only 14.5% of the time at a 50-passage budget. Put a capable model in the loop — read the first results, name the missing bridge fact, re-query, rerank — and full-chain recall rises to 56.5% at the same budget: a 3.9× improvement. The retriever is cloud-free; the only model calls are the in-loop reasoning ones.Na plnom LoCoMo benchmarku (276 multi-hop otázok) ploché vyhľadávanie podľa podobnosti poskladá celý dôkazový reťazec len v 14.5 % prípadov pri rozpočte 50 pasáží. Daj schopný model do slučky — prečítaj prvé výsledky, pomenuj chýbajúci most, znova sa opýtaj, prerob poradie — a recall celého reťazca stúpne na 56.5 % pri rovnakom rozpočte: zlepšenie 3.9×. Vyhľadávač je cloud-free; jediné volania modelu sú tie uvažovacie v slučke.

The problem

Long-conversation memory is the bottleneck for agents that need to remember. The hard case is multi-hop questions — ones whose answer requires chaining 2+ facts stated in different turns ("Where did the person Caroline started dating in 2023 grow up?"). We measured how often plain dense retrieval pulls all the required evidence turns into a fixed 50-passage context, on LoCoMo (conversations averaging ~597 turns):

  • single-hop full-evidence recall@50: 0.665
  • multi-hop full-evidence recall@50: 0.145

Multi-hop is where retrieval breaks. And it is not because the evidence is missing — a diagnostic showed the gold turns are present in the pool but rank-buried: recall@100 = 0.514, recall@150 = 0.641, recall@200 = 0.736, while the answer needs only ~3 turns on average (mean gold size 3.17). It is a ranking problem, not a coverage problem — which tells you exactly what to fix.

The method — capability in the loop, not a fancier static mechanism

Elaborate static memory mechanisms (decision-trace, multi-agent voting, bi-temporal consolidation) mostly don't survive a capable model. What does work is the opposite: use the model's reasoning inside the retrieval loop. Four compounding stages, all at the same 50-passage budget:

stagefull-recall@50 (n=276)× flat
flat top-50 (dense, question only)0.1451.0×
+ LLM-in-the-loop follow-up queries0.2972.0×
+ better fusion (RRF over the follow-up queries)0.3262.25×
+ LLM reranker (pick the chain from a top-100 pool)0.4823.3×
+ adaptive multi-round + rerank a deeper pool0.5653.9×

1. Follow-ups in the loop. Round-1 retrieves the top-15 by question similarity. The model reads them, identifies the bridge entity the question needs but round-1 didn't surface, and emits 1–2 concrete follow-up queries; we retrieve those and fuse. (0.145 → 0.297.)

2. Fusion that targets the bridge. Combining by Reciprocal Rank Fusion over the follow-up queries only — dropping the original question ranking — beats every other fusion. The question over-retrieves the obvious hops round-1 already had; the follow-ups target what's missing. (→ 0.326.) Note: asking for more queries hurt — it dilutes the fusion; 1–2 sharp bridge queries are optimal.

3. The reranker. Give the model a top-100 candidate pool and ask it to select the turns that form the full evidence chain, recall-oriented. This promotes gold turns retrieval buried at rank 50–100 into the kept 50. (→ 0.482, recovering 43 questions.)

4. Adaptive multi-round. A second reader sees what's already retrieved and names what's still missing → new queries → re-fuse into a deeper top-150 pool → rerank that. (→ 0.565.)

Why the comparison is fair

  • Equal budget. Every method returns exactly 50 passages, scored on the same full-evidence recall@50. The lift is not "retrieve more."
  • No leakage. The in-loop reader sees only the question and the already-retrieved turns — never the gold evidence. The follow-ups are inferred, not looked up.
  • Judge-free metric. Full-evidence recall is exact set-containment against LoCoMo's annotated evidence — no LLM judge, fully reproducible.
FalsifierIf the in-loop follow-ups had been retrievable by the original question alone, the lift would be an artifact of "more queries." They are not: stage 2 shows that dropping the question and fusing only the inferred bridge queries is what wins, and asking for more queries regresses. And if the reader had seen the gold evidence, the gain would be leakage — it sees only the question and round-1.

Honest caveats: absolute recall is ~57%, not solved — a large relative gain and a robust direction, not a finished memory system. Stages 1, 3, 4 are per-query model calls — a real cost/recall knob, not free (stage 2, fusion, is free). One dataset (LoCoMo is two-person conversations, where the bridge entity — a name — is relatively easy to name; multi-entity corpora may be harder). Every number above comes from a runnable experiment; the retriever uses local embeddings only.

Problém

Pamäť dlhých konverzácií je úzke hrdlo pre agentov, ktorí si majú pamätať. Ťažký prípad sú multi-hop otázky — tie, ktorých odpoveď vyžaduje zreťaziť 2+ fakty uvedené v rôznych replikách ("Kde vyrástol človek, s ktorým Caroline začala chodiť v roku 2023?"). Odmerali sme, ako často ploché husté vyhľadávanie dostane všetky potrebné dôkazové repliky do pevného kontextu 50 pasáží, na LoCoMo (konverzácie majú priemerne ~597 replík):

  • single-hop full-evidence recall@50: 0.665
  • multi-hop full-evidence recall@50: 0.145

Multi-hop je miesto, kde sa vyhľadávanie láme. A nie preto, že by dôkazy chýbali — diagnostika ukázala, že gold repliky sú v poole, len zahrabané v poradí: recall@100 = 0.514, recall@150 = 0.641, recall@200 = 0.736, pričom odpoveď potrebuje v priemere len ~3 repliky (priemerná veľkosť gold 3.17). Je to problém poradia, nie pokrytia — čo presne hovorí, čo opraviť.

Metóda — schopnosť v slučke, nie ozdobnejší statický mechanizmus

Prepracované statické pamäťové mechanizmy (decision-trace, hlasovanie viacerých agentov, bi-temporálna konsolidácia) väčšinou neprežijú schopný model. Funguje opak: použiť uvažovanie modelu vnútri slučky vyhľadávania. Štyri sčítavajúce sa fázy, všetky pri rovnakom rozpočte 50 pasáží:

fázafull-recall@50 (n=276)× flat
flat top-50 (husté, len otázka)0.1451.0×
+ follow-up dopyty s modelom v slučke0.2972.0×
+ lepšia fúzia (RRF cez follow-up dopyty)0.3262.25×
+ LLM reranker (vyber reťazec z top-100 poolu)0.4823.3×
+ adaptívny multi-round + rerank hlbšieho poolu0.5653.9×

1. Follow-upy v slučke. Round-1 vytiahne top-15 podľa podobnosti k otázke. Model ich prečíta, určí mostovú entitu, ktorú otázka potrebuje, ale round-1 ju nevyniesol, a vydá 1–2 konkrétne follow-up dopyty; tie vyhľadáme a zfúzujeme. (0.145 → 0.297.)

2. Fúzia mieriaca na most. Kombinovanie cez Reciprocal Rank Fusion len cez follow-up dopyty — s vynechaním pôvodného poradia podľa otázky — poráža každú inú fúziu. Otázka nadmerne vyťahuje očividné hopy, ktoré round-1 už mal; follow-upy mieria na to, čo chýba. (→ 0.326.) Pozn.: žiadať viac dopytov uškodilo — riedi to fúziu; 1–2 ostré mostové dopyty sú optimum.

3. Reranker. Daj modelu top-100 kandidátsky pool a nechaj ho vybrať repliky, ktoré tvoria celý dôkazový reťazec, s dôrazom na recall. To povýši gold repliky, ktoré vyhľadávanie zahrabalo na poradí 50–100, do ponechaných 50. (→ 0.482, získaných späť 43 otázok.)

4. Adaptívny multi-round. Druhý čitateľ vidí, čo je už vytiahnuté, a pomenuje, čo stále chýba → nové dopyty → re-fúzia do hlbšieho top-150 poolu → rerank toho. (→ 0.565.)

Prečo je porovnanie férové

  • Rovnaký rozpočet. Každá metóda vráti presne 50 pasáží, hodnotí sa rovnaký full-evidence recall@50. Zisk nie je "vytiahni viac."
  • Žiadny únik. Čitateľ v slučke vidí len otázku a už vytiahnuté repliky — nikdy nie gold dôkazy. Follow-upy sú odvodené, nie vyhľadané.
  • Metrika bez sudcu. Full-evidence recall je presné množinové obsiahnutie voči anotovaným dôkazom LoCoMo — žiadny LLM sudca, plne reprodukovateľné.
FalzifikátorAk by follow-upy v slučke boli vyhľadateľné už samotnou pôvodnou otázkou, zisk by bol artefaktom "viac dopytov." Nie sú: fáza 2 ukazuje, že vynechanie otázky a fúzia len odvodených mostových dopytov je to, čo vyhráva, a žiadať viac dopytov zhoršuje. A keby čitateľ videl gold dôkazy, zisk by bol únik — vidí len otázku a round-1.

Čestné výhrady: absolútny recall je ~57 %, nie vyriešené — veľký relatívny zisk a robustný smer, nie hotový pamäťový systém. Fázy 1, 3, 4 sú per-query volania modelu — reálna páka cena/recall, nie zadarmo (fáza 2, fúzia, je zadarmo). Jeden dataset (LoCoMo sú dvojosobové konverzácie, kde mostová entita — meno — sa dá pomenovať relatívne ľahko; korpusy s viacerými entitami môžu byť ťažšie). Každé číslo vyššie pochádza z bežateľného experimentu; vyhľadávač používa len lokálne embeddingy.
